# 旧英文站功能与新基座承载评估

日期：2026-10-20

方法：只读查库与代码追踪；未登录旧后台操作、未修改旧库或旧站。检查时临时启动本机 MySQL 5.7，结束后已停止。本文不包含账号、密钥和会员个人资料。

## 结论

当前 Next.js + Directus 11 + MySQL 8 的分层可以承接旧英文站并继续扩展，**不需要因为旧后台菜单多就整体改技术栈**。但当前交付仍是基座和部分运营试点，距离完整替换旧站有大量业务功能与数据迁移工作。Directus 应承担内容、字段、文件和运营编辑；会员认证、受控下载、个人中心、搜索与部分复杂流程由独立业务代码实现。若要求所有旧功能都只靠 Directus 原生界面完成，项目风险会明显增加。

决定项目能否做大的是：按页型建模和迁移、后台真实操作体验、旧会员身份承接、大数据量分页/索引/搜索、生产部署与回滚。需要尽早完成最难功能的端到端样本，再扩大迁移范围。

## 已确认的“后台可配置 → 前台显示”链路

1. **栏目与导航**：`hr_category` 保存父子关系、排序、启停、URL、栏目模板、SEO 等字段；解决方案模板 `xhr/Template/default/category/solution_industryNew.html` 通过 `<xhr:nav parentid="3">` 生成子导航。服务、关于、产品同样有栏目树。新基座可用 Directus 分类/页面/板块集合承接，但旧 URL 与栏目 ID 要建立映射。
2. **首页模块**：`xhr/Template/default/index.html` 含首页 Banner、产品中心、新产品通讯、定制服务、新闻中心、解决方案的数据绑定占位符。对应本地栏目 `11/12/13/14` 各有 5/6/5/2 条内容。新基座的 `home_blocks` 已覆盖部分展示配置，但需逐项对照旧模块字段、排序、图片和链接。
3. **解决方案与服务**：本地数据库有工业自动化、电力、风电等解决方案栏目；FAQ 13 条、认证与证书 21 条、产品目录 4 条、展会 14 条。旧模板的服务研发能力页绑定多个栏目和模块。新基座的 `site_pages`、`page_sections` 已有试点，但旧站的独立子页、FAQ 和下载中心尚未完整承接。
4. **新闻、联系与营销页**：栏目可指定 `tpl_list` / `tpl_detail`；`about_contact.html` 从内容记录的标题、图片和多个文本字段渲染联系页。当前 `site_pages` 能承接可配置内容，但需要以业务字段重新建模，不能把旧 `text1/text18` 等字段原样暴露给运营。
5. **产品详情**：`xhr/Template/default/category/product_content_lines20.html` 明确含总览、技术数据、附件、认证、商业数据、下载、配套/关联/近似产品，以及图片、收藏、对比、PDF。当前 `product_spec`、`product_certification`、`product_document`、`product_relation` 及前台展示已有工作区试点，尚未完成旧数据全量迁移与运营验收。
6. **会员与个人中心**：旧站前台有登录、注册、找回密码、资料、我的下载、收藏、对比、浏览历史等页面；后台有会员、会员组、审核和会员模型。当前新基座尚无前台会员认证与会员数据承接，这是完整上线硬门槛。

旧站通过后台保存内容并生成静态 HTML；根目录里的 `index.html` 和大量 `content/details_*.html` 是生成结果，不能据其存在断言内容写死。新站以 Directus 数据和 Next.js 页面/缓存替代“手工生成整个站点”，不需要复刻旧生成器。

## 下载登录：本次核对与需求裁决

用户确认：**旧官网资料下载需要注册登录，新官网必须保持这一规则**。旧前台 JS `statics/js/member.js:getIsLogin()` 会把部分资料入口转向会员登录；`xhr/Template/default/category/product_content_lines20.html` 也有“下载”和“我的下载”关联。另一方面，`xhr/Lib/Action/Contents/IndexAction.class.php:downloadFile()` 本身未见明确的登录拒绝分支，登录态用于写入 `userDownload()`；本地模板里还有直接链接。仅据代码无法判定现网是否还有网关、前台交互或其它拦截，也不能把接口实现当成产品规则。

新站按用户确认的规则实现：**服务端在每个实际文件下载入口验证会员会话**；未登录不能通过直接请求、猜测 URL 或绕过前台按钮获得文件；登录后记入“我的下载”。旧站各类文件的范围、会员组差异和实际文件来源还需核实。

## 承载方式与风险

| 旧能力 | 新方案中的位置 | 当前判断 |
|---|---|---|
| 栏目、内容、翻译、SEO、图片、新闻、FAQ、营销页 | Directus 集合 + Next.js 页型 | 架构合适；已有一部分，需逐页型补齐和做编辑体验验收 |
| 产品参数、认证、附件、下载元数据、关联 | SKU 子集合 + 前台聚合层 | 架构合适；当前是试点，难点在旧数据映射和大规模导入 |
| 后台批量导入、审核、复杂编辑器和预览 | Directus 扩展及受控后台模块 | 可以实现，但不能假定原生控件足够；要提前做真实操作样本 |
| 会员账号、登录、个人中心、收藏、历史、下载记录 | 独立会员业务表/认证逻辑，后台提供管理入口 | 当前缺失；特别要先确认真实账号库及跨语言账号关系 |
| 搜索、PDF/图片分发、静态生成替代 | 搜索服务、对象存储/CDN、Next.js 缓存 | 技术上可扩展；生产负载、索引和缓存失效需压测 |
| 评论、问卷、营销群发、第三方登录 | 按真实使用决定独立业务模块或外部服务 | 有代码/菜单不等于必须原样迁移；评论本地数据为 0，问卷有数据 |

### 必须提前验证的四条链路

1. **会员**：确认旧真实账号库，抽样迁移旧哈希、资料、会员组，并走完登录、注册、找回、停用和跨语言访问。
2. **受控下载**：一个真实 SKU 的文件由后台上传/关联，经前台登录后下载并写“我的下载”；未登录直接请求被服务端拒绝。
3. **复杂产品**：一个 SKU 的图片、参数、认证、附件、下载、关联在 Directus 真实编辑页可维护，在前台正确展示。
4. **批量运营与性能**：按英文副本及其它语言的目标数据量做导入预览、错误报告、分页、搜索索引和压力测试；验证发布后缓存更新。

四条链路通过后，Directus 不能承载核心需求的风险会大幅降低；若某条需要反复修改 Directus 内部源码，应把该业务留在独立模块，Directus 仅承担内容与必要的运营入口。此处的“可行”是基于代码和本地副本的架构判断，不是生产容量或上线验收结论。

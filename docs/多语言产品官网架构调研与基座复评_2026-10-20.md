# 多语言产品官网架构调研与基座复评

日期：2026-10-20。范围：官网型产品目录、约 13,098 个订货号、多语言内容与会员受控下载；对照 `D:\degson-pilot` 当前工作区及 `E:\degsonen\degsonEn` 旧英文站本地副本。本文是架构判断，不是生产压测或上线验收。

## 结论

**继续采用 Next.js + Directus + MySQL 的当前基座是可行的**，但应把 Directus 定位为内容与产品编辑后台，而不是所有业务的唯一运行时。搜索、会员认证、受控下载及复杂导入应有明确的独立实现。约一万三千 SKU、预计不超过一千人同时在线，均不构成必须改用大型 PIM 或整体重写的证据；并发承载能力仍须用实际页面、搜索和下载流量压测确认。

最值得提前固定的是产品主数据边界：产品/系列稳定 ID、属性定义、单位与类型、分类适用范围、SKU 变体轴、翻译状态、文件权限。若这些规则正确，日后加专用 PIM 可以让其作为产品数据上游，前台与搜索层无需推倒重做。

## 代表性成熟方案的共性

1. **PIM 或结构化产品库管理产品主数据。** Akeneo 明确建模产品族、族变体、属性、语言和渠道；Pimcore 的 Classification Store 处理类别差异很大的动态属性及其本地化。这说明复杂目录的关键是属性治理与变体规则，并非把每个 SKU 做成一篇自由格式文章。[Akeneo 产品族与变体](https://help.akeneo.com/en_US/serenity-build-your-catalog/30-serenity-manage-your-families-and-variant-families)、[Akeneo 属性](https://help.akeneo.com/en_US/serenity-build-your-catalog/serenity-manage-your-attributes)、[Pimcore Classification Store](https://docs.pimcore.com/platform/Pimcore/Objects/Object_Classes/Data_Types/Classification_Store/)
2. **CMS 管营销内容与运营页面。** Directus 基于关系型数据库，可建主表和翻译表；其扩展机制支持自定义后台控件、模块、Hook 和 API。它适合当前官网内容及产品目录的运营入口，但产品质量流程是否够用，要用真实批量编辑样本检验。[Directus 数据模型](https://docs.directus.io/app/data-model)、[Directus 关系与翻译](https://docs.directus.io/app/data-model/relationships)、[Directus 扩展](https://docs.directus.io/guides/administration)
3. **搜索与筛选使用派生索引。** 适合按语言、分类、极数、间距等字段建立搜索文档与可筛选属性。Meilisearch 支持全文检索和分面筛选；索引应由主数据更新驱动，并具备全量重建和一致性校验，不把搜索索引当主库。[Meilisearch 分面搜索](https://www.meilisearch.com/products/faceted-search)
4. **公开页面缓存，会员操作动态校验。** Next.js 的 ISR 可按需生成大量内容页，避免每次发布重建全站。多实例部署时必须协调共享缓存与失效；Directus 多容器部署需 Redis。[Next.js ISR](https://nextjs.org/docs/app/guides/incremental-static-regeneration)、[Next.js 自建部署](https://nextjs.org/docs/app/guides/self-hosting)、[Directus 配置](https://docs.directus.io/self-hosted/config-options)

这不是唯一的“标准产品组合”。当企业要向多个网站、电商、经销商或 ERP 同步一套复杂商品资料，并依赖数据完整度、审批、多团队翻译和渠道差异时，专用 PIM 的价值上升。若主要目标仍是一个多语言官网，现有关系模型与 Directus 编辑层可先承担产品资料，不必为了 SKU 数量提前引入整套 PIM。

## 对当前基座的复评

- **方向正确：** 已有 `category` / `series` / `product` 与翻译表；`product_spec`、认证、附件、关联作为子集合试点；Next.js 前台有 ISR 60 秒。当前记录的迁移目标约为 3,614 系列、13,098 订货号、147,250 全语言变体行，旧英文副本还有 219,830 条混合内容行；这些不是同一种记录，不能直接相加当 SKU 数。[项目交接](../PROJECT-HANDOFF.md)、[旧英文站核查](./旧英文站功能与新基座承载评估_2026-10-20.md)
- **产品模型缺口：** 目前 `product_spec` 以每行一条参数保存 `kind`、`group_key` 和翻译后的标签、值、单位。展示试点够用；大规模筛选、批量导入、单位换算和属性一致性需要独立属性定义表、字段类型、可选值、适用产品族及校验规则。SKU 与系列的变体轴也要明确。
- **搜索未落地：** 项目交接将 Meilisearch 列为 M2，当前没有可用于生产的索引构建、增量同步、索引重建及搜索压测。
- **会员与下载是上线硬门槛：** 当前 `web/src/app/api/product-document/[orderNo]/[fileId]/route.ts` 检查产品与文档关系，但未验证会员会话，且回复 `public, max-age=60`。按照已确认的业务规则，它不能作为正式受控下载入口。应由服务端认证、授权、记下载记录后，再从私有文件存储读取或签发短时链接，并禁止绕过业务接口直取受控文件。
- **生产运维未完成：** 本地 `docker-compose.yml` 不是生产拓扑。需设计对象存储、备份恢复、监控告警、发布回滚、权限和密钥管理，以及多实例时 Redis 与缓存协调。并发人数不是每秒请求量，也不能据此承诺某个服务器规格。

## 建议的决策关口

继续现有基座，但在全量迁移之前完成四个可测样本：一个复杂产品族的 SKU/属性/多语言导入和编辑；全目录搜索与典型筛选；旧会员迁移抽样及未登录/已登录下载；发布后的缓存更新和预期流量压测。若编辑效率、属性治理或多渠道分发要求超出 Directus 编辑层能力，优先增加专用 PIM 作为上游，而不是更换整个前台技术栈。

## 1. 文档目的

本 PRD 用于定义 DEGSON 新官网正式建设前的产品、内容、后台、多语言、GEO/SEO、部署和验收边界。

本版本重点补充并明确：

1. 多语言继续采用独立语言域名，但不复制多套项目。
2. 前台使用一套 Next.js 代码，后台使用一个 Directus。
3. 多语言内容以同一条业务数据下的翻译记录管理。
4. 域名、canonical、hreflang、sitemap 和语言切换必须在设计阶段确定。
5. 后台必须面向运营人员，不得暴露 UUID、内部枚举值或原始数据库字段语义。
6. 图片必须支持上传、预览、替换、清除，并且历史外链不能遮挡或破坏编辑页面布局。
7. 后台列表数据必须支持可控的批量导入和导出，降低产品、FAQ 等内容的录入和维护成本。
8. 后台导航菜单必须支持按运营需要配置显示、隐藏、排序和分组，但菜单配置不能替代数据权限。
9. 盘点现网第三方登录渠道，明确会员账号承接、跨域回调与密钥管理；旧后台存在配置入口不等于该渠道必须迁移。
10. 逐页承接旧站 GEO/SEO 编辑能力：运营可按语言配置可见 H1、浏览器 Title、Meta Description 与安全的 Schema 内容，并能在发布后核对实际输出。
11. 前台会员登录及会员管理是新官网整体上线的必备能力；旧会员账号和资料必须有经验证的承接方案。

本文件是需求和架构约束，不等于立即开发任务清单。正式开发前需要先完成模型、字段、域名和迁移映射评审。

## 2. 项目目标

### 2.1 业务目标

- 重建 DEGSON 官网，保留现有产品、分类、系列、新闻和下载等核心业务能力。
- 保留前台会员登录及会员管理，保证现有会员在新官网切换后仍能使用账号。
- 解决旧官网“每个语言独立 PHP 项目”的重复维护问题。
- 让运营人员在一个后台内管理所有语言内容。
- 让新增语言不需要复制项目、不需要新增后台、不需要重复开发页面。
- 让产品目录、技术资料和营销内容具备结构化、可检索、可持续维护能力。
- 让搜索引擎和 AI 爬虫能够理解语言、产品层级、产品参数和页面关系。

### 2.2 技术目标

- 前台不直接连接数据库，只通过 Directus API 获取内容。
- 一套前台代码支持多个语言域名。
- 一个 Directus 后台承载所有语言和所有内容配置。
- 数据模型、字段元数据、权限、扩展和初始化脚本可以从仓库重建。
- 内容变更后可以按路径进行增量刷新，不依赖人工批量生成静态页面。

## 3. 总体架构

```text
用户访问语言域名
        ↓
阿里云 DNS / CDN / HTTPS
        ↓
同一个 Next.js 前台服务
        ↓
Host 识别语言 → 内部 rewrite 到 /[lang]/...
        ↓
Directus API
        ↓
MySQL 8
```

### 3.1 服务数量

| 服务 | 数量 | 说明 |
|---|---:|---|
| Next.js 前台 | 1 套 | 根据域名识别语言，不复制项目 |
| Directus 后台 | 1 套 | 所有语言共用一个后台 |
| MySQL | 1 套 | 主数据和翻译数据统一存储 |
| 搜索服务 | 1 套 | 多语言索引，按语言过滤 |
| CDN | 1 套 | 绑定多个语言域名 |

### 3.2 后台原则

Directus 是唯一后台入口。

不再为中文、英文、德语等语言分别创建后台项目。需要特殊业务体验时，使用 Directus 自定义 interface、layout 或 module 扩展，而不是再建设第二套后台。

## 4. 多语言与域名方案

### 4.1 目标域名模型

语言域名以配置为准，以下为示例：

| 语言代码 | hreflang | 域名示例 | URL 形态 |
|---|---|---|---|
| `en` | `en` | `https://www.degson.com` | `/product/...` |
| `zh` | `zh-Hans` | `https://www.degson.com.cn` | `/product/...` |
| `de` | `de` | `https://de.degson.com` | `/product/...` |
| `fr` | `fr` | `https://fr.degson.com` | `/product/...` |
| `es` | `es` | `https://es.degson.com` | `/product/...` |

最终语言域名以业务确认的域名清单为准，不允许在代码中散落硬编码。

### 4.2 内部路由

前台内部统一使用：

```text
/[lang]/...
```

例如：

```text
https://de.degson.com/product/category/terminal-blocks
```

在 Next.js 内部解析为：

```text
/de/product/category/terminal-blocks
```

用户地址栏保留语言域名，不展示 `/de` 前缀。

### 4.3 域名识别规则

1. 根据请求 `Host` 在语言域名映射表中查找语言。
2. 找到后 rewrite 到对应的内部语言路由。
3. 访问错误语言前缀时 301/308 到该域名的 canonical URL。
4. 未知域名进入默认英文站，或由部署层拒绝，不能随机选择语言。
5. staging 环境使用独立域名映射，不得把 staging URL 输出到生产 canonical。

### 4.4 语言切换

语言切换必须跳转到同一业务内容的对应语言域名，并使用目标语言翻译记录自己的 slug：

```text
www.degson.com/products/terminal-blocks/pcb-plug/9edgk-5-0
→ www.degson.com.cn/products/接线端子/PCB插头/可插拔式接线端子系列
```

如果目标语言没有对应翻译：

- 不生成错误语言页面；
- 明确跳转到默认语言页面；
- canonical 和 hreflang 只声明真实存在的语言版本；
- 页面可以提示“当前语言暂无内容”。

### 4.5 必须写入配置的内容

```ts
type LanguageSite = {
  code: string;
  htmlLang: string;
  hreflang: string;
  origin: string;
  enabled: boolean;
};
```

语言域名表必须成为配置单一来源，供以下模块共同使用：

- middleware
- canonical
- hreflang
- sitemap
- Open Graph URL
- JSON-LD URL
- 语言切换器
- 301 旧地址映射

### 4.6 URL slug 规范（强制）

所有公开内容详情页必须使用可读、按语言本地化的 slug 作为 URL 标识。不得把数据库 ID、UUID、纯数字主键或内部编码作为详情页唯一 URL。至少覆盖分类、系列、SKU 产品、新闻、FAQ、下载资料和解决方案详情；新增公开内容页型也遵守本规范。slug 来自该内容对应语言的翻译记录。

产品目录 URL 必须体现真实分类层级，不得把通用页型词 `category` 或 `series` 当作内容路径的中间层级。产品分类使用从一级到当前级的完整分类 slug 路径；系列详情在完整分类路径后追加系列翻译 slug；SKU 详情在系列路径后再追加产品翻译 slug。不存在的分类层级直接省略，不虚构路径段。统一形态如下（分类层级按实际数据增减）：

```text
/products/{一级分类 slug}/{二级分类 slug}/{三级分类 slug}
/products/{一级分类 slug}/{二级分类 slug}/{三级分类 slug}/{系列 slug}
/products/{一级分类 slug}/{二级分类 slug}/{三级分类 slug}/{系列 slug}/{SKU slug}
```

分类、系列和 SKU 路径中的每个段均取当前语言对应的已发布翻译记录；语言切换必须解析到同一业务内容的目标语言层级路径。路径层级必须与 Directus 中真实的分类父子关系、系列所属分类和 SKU 所属系列一致。

示例：

```text
英文新闻标题：DEGSON Launches New Push-in Terminal Blocks!
英文 URL：/news/degson-launches-new-push-in-terminal-blocks

中文新闻标题：高松推出全新 Push-in 接线端子！
中文 URL：/news/高松推出全新Push-in接线端子
```

Slug 生成、维护和路由规则：

- 每种语言独立生成并保存 slug；语言切换按同一内容主记录匹配目标语言翻译，再跳转到目标翻译的 slug，不能把当前语言的 slug 原样拼到另一语言域名。
- 中文 slug 保留标题中的汉字、英文字母和数字；移除标点、空格及其他不适合 URL 的特殊符号，不将中文强制转拼音。标题中的空白可规范为连字符；连续或首尾连字符须折叠或移除。
- 英文及其他拉丁文字 slug 转小写；去除重音符号，空白和词间标点规范为单个连字符，移除其余不安全字符。其他语言保留本语言文字；所有 slug 统一执行 Unicode 规范化、空值检查和 URL 编码。
- 新建翻译内容时，系统根据该语言标题生成初始 slug，并允许有权限的运营人员在 Directus 中编辑。slug 在同一语言、同一页型路由范围内必须唯一；发生冲突时系统提示并生成可读的唯一后缀，不得静默覆盖或发布冲突 URL。
- 首次发布后 slug 默认保持稳定。仅修改标题不得自动改变已发布 URL。运营人员主动修改已发布 slug 时，系统必须保存旧路径到新 canonical URL 的 301 映射；映射需避免循环和链式跳转，并在发布时同步刷新 canonical、hreflang、sitemap、Open Graph、JSON-LD URL 及相关缓存。
- 现有以 ID、订货号或旧 slug 访问的地址必须通过 301 跳转到对应语言的当前 canonical slug URL。找不到目标内容时返回 404，不得按猜测跳转到其他内容。
- slug 使用翻译记录管理，纳入数据导入导出、备份、迁移和版本记录；前台不得在每次请求时临时根据标题生成 slug。

## 5. 内容和数据模型

### 5.1 主数据与翻译数据

采用“主数据 + 翻译行”模型：

```text
category
 └── category_translations

series
 └── series_translations

product
 └── product_translations

news
 └── news_translations

home_banner
 └── home_banner_translations
```

首页 Banner 以一条主记录代表一个推广内容，各语言文案在该记录下维护翻译；后台主列表不按语言重复展示同一 Banner。排序、整体发布状态和业务跳转目标由主记录管理；标题、简介、按钮文字、该语言内容状态及确有本地化需求的图片由翻译记录管理。图片默认可共用，若素材内含文字或各语言展示要求不同，允许单个语言覆盖。缺少该语言已发布内容时不直接展示另一语言文案。

所有公开内容翻译记录均须有独立的 `slug` 字段。slug 遵循 §4.6，按语言生成、唯一校验并稳定保存；不可只在前台用标题临时拼接，也不可用主记录 ID、UUID 或订货号替代本地化 slug。

语言字段统一使用短码：

```text
en / zh / de / fr / es
```

不得在同一项目中混用 `en-US`、`zh-CN` 和 `en`、`zh` 作为业务语言码。

### 5.2 产品层级

```text
产品分类
  └── 产品系列
        └── SKU / 订货号
              ├── 基础参数
              ├── 技术参数
              ├── 产品图片
              ├── 认证资料
              ├── 附件与下载
              └── 关联产品
```

### 5.3 图片字段要求

所有分类、系列、新闻、产品和资料图片字段必须满足：

- 空值状态明确；
- 上传图片；
- 替换图片；
- 清除图片；
- 预览图片；
- 显示合理的文件信息；
- 历史外链可以兼容，但不能把完整 URL 压在图片上；
- 长 URL 必须在独立信息区域换行或截断；
- 正式新增图片优先进入 Directus 文件库；
- 前台通过安全媒体解析器输出图片地址。

### 5.4 枚举和关联字段

- 有限枚举必须使用中文下拉，不得让运营输入内部 code。
- 布尔值使用开关或复选框。
- 关联字段显示分类名、系列码、订货号或标题，不显示内部 ID。
- 排序字段显示“显示顺序”等业务名称。
- 语言字段使用语言选择，不要求运营手填语言码。

## 6. Directus 后台需求

### 6.1 后台范围

第一阶段必须覆盖：

- 产品分类及分类图片
- 产品系列及系列图片
- SKU 基础信息
- SKU 主图、详情图、工程图
- 新闻及新闻封面
- FAQ 及 FAQ 多语言内容
- 多语言翻译行
- SEO 标题、描述、关键词和结构化内容
- 各公开页型的逐页、逐语言 GEO/SEO 编辑入口与预览（详见 §6.6、§8.4）
- 文件库和下载资料
- 用户、角色和权限
- 批量导入、导出和导入错误报告
- 可配置的后台业务导航菜单
- 第三方登录渠道清单与配置管理（具体渠道及上线阶段以现网使用核查结果为准）
- 前台会员账号、资料和状态管理；前台会员与 Directus 后台管理员必须区分
- 首页 Banner 管理及其多语言内容（见 §6.1.2）

后续阶段补齐：

- 技术参数
- 产品认证
- 认证图片
- 产品附件
- 商业数据
- 配套产品
- 关联产品
- 相似规格产品
- 产品选型配置
- 其他栏目素材及扩展展示方式
- 会员下载权限的扩展规则（现网在用的基础权限须随首期承接）

### 6.1.1 会员上线门槛

新官网整体替换旧官网前，必须交付前台会员登录、注册、找回密码、退出登录、个人资料查看与修改，以及后台会员查询、审核或状态管理。旧会员账号、身份标识、基础资料和会员组应完成迁移、去重、对账；现有会员应能继续登录，确实无法安全沿用的密码必须提供可用的重置流程。不得仅迁移会员名单、仅使用 Directus 后台用户，或以登录页面演示代替真实账号验收。

所有语言站使用同一套前台会员主数据和同一个后台会员管理入口。会员身份、资料、账号状态、会员组、下载权限和“我的下载”记录均按会员统一管理；语言仅影响界面和可选的沟通偏好，不产生中文会员、英文会员两套账号。迁移旧中文站与英文站会员时，应以经过核实的身份标识做匹配、去重与冲突人工复核，不能仅凭相同姓名自动合并，也不能因来源语言不同重复建号。不同顶级域名之间是否自动保持登录状态属于会话方案，须单独设计和验收，不改变统一账号原则。

官网资料下载须先完成注册并登录；未登录访问下载入口或直接请求下载接口均不得取得文件，登录后应记录到会员的“我的下载”。具体文件范围及会员组差异仍须对照旧站核实。询盘等其他会员权益按现网流程核实并承接。前台会员认证应与内容编辑权限隔离。第三方登录渠道是否进入首期，以 §6.5 的现网使用核查为准，但不影响基本账号登录这一上线门槛。

上线验收至少覆盖旧会员登录、首次注册、找回密码、资料修改、停用账号、重复邮箱或手机号处理、跨语言访问、未登录下载拦截、登录后下载及“我的下载”记录，以及后台按权限查看和处理会员；用脱敏迁移样本与经授权的真实账号抽样验证。会员数据迁移与旧站切换需有回滚方案。

### 6.1.2 首页 Banner 管理

- 后台提供清楚的“首页 Banner”业务入口；同一个 Banner 在列表只显示一条，可查看显示顺序、整体状态及中英文内容完成情况。
- 打开该条记录可维护各语言标题、简介和按钮文字，上传、预览、替换、清除共用图片；确需不同语言素材时允许翻译记录覆盖图片。
- 支持多张 Banner 的显示顺序和发布控制。跳转目标优先选择站内页面、产品分类或系列等业务对象，由前台生成对应语言地址；外部地址作为明确的特殊类型处理，不让运营以手填旧站 URL 作为主要操作路径。
- 前台只展示当前语言已完成且可发布的 Banner；后台编辑、发布后应能分别核对中英文首页的文案、图片、顺序和跳转结果。视频、定时发布等能力在核实现网实际使用后确定是否进入首期。

### 6.2 后台体验

后台页面必须优先满足运营正确操作，而不是优先暴露数据库完整字段。

验收标准：

- 主要页面中文显示；
- 不出现无意义的内部字段名；
- 不要求填写 UUID；
- 不要求填写内部枚举值；
- 图片可直接上传和预览；
- 关系字段可以按业务名称选择；
- 长表单有合理分组；
- 移动端不是主要后台场景，但窄屏不能出现字段重叠、遮挡和横向溢出。

#### 6.2.1 页面集中编辑与可读性

- 运营从“首页、服务、关于我们”等业务页面入口进入后，应能在该页面的编辑路径内找到页面文案与图片、页面板块、各语言 H1/SEO 字段和预览入口；不要求为同一页面在多个无关联列表间反复查找。
- 前台导航只维护菜单层级、显示名称、排序及目标页面，不复制页面正文或 SEO。具有独立公开 URL 的二级栏目按独立页面管理；只在父页内切换的 Tab/锚点作为页面板块管理，不重复配置独立页面 H1、Title 和 Schema。
- 普通运营可见的集合、字段、选项和帮助文字必须使用可理解的中文业务名称；“数据 1”“介绍 1”等不说明用途的通用名称须按真实页面语义改名或仅在适用模块显示。内部 ID、语言码、技术字段和不适用字段不得作为主要编辑界面。
- 服务页作为首个验收样本：运营在“服务页”入口内完成中英文页面文案、子板块及 SEO 的编辑、保存、重开和前台预览；验收记录实际操作步骤、找不到入口或误填字段的情况，再推广到其他固定页。

### 6.3 列表数据导入与导出

后台必须提供面向运营人员的列表数据导入和导出能力，优先覆盖产品、产品系列、产品分类、新闻、FAQ、下载资料元数据及其翻译内容。该能力用于批量维护结构化内容，不用于绕过权限、直接写入数据库或批量上传二进制文件。

#### 6.3.1 导入范围

- 支持从 XLSX 和 CSV 导入；默认提供与当前数据模型一致的下载模板。
- 导入模板必须包含业务字段名、字段说明、是否必填、示例值、语言和父级关联说明，不要求运营人员填写 UUID。
- 支持主数据和翻译数据的导入；翻译行必须通过业务唯一键、语言和父级业务键匹配，不得只依赖内部 ID。
- 产品导入至少覆盖：分类、系列、订货号、标题、摘要、状态、排序、语言、SEO 字段以及可引用的图片/文件业务标识。
- FAQ 导入至少覆盖：所属栏目或产品范围、问题、答案、语言、显示状态、排序和 SEO 字段。
- 导入前必须执行格式校验、必填校验、枚举校验、关联校验、唯一性校验和语言校验；校验失败时不得部分写入，除非用户明确选择系统支持的“成功行提交”模式。
- 导入结果必须提供成功数量、失败数量、失败原因和原始行号，并支持下载错误行报告。
- 导入必须保留操作人、时间、文件名、目标集合、导入模式和结果摘要，便于追溯。
- 对已有数据必须明确区分“新增”“更新”和“跳过”；默认不得因字段为空而清空已有内容，清空必须由模板中的明确操作标记触发。

#### 6.3.2 导出范围

- 支持按当前列表筛选条件、语言、状态、分类、系列和发布时间导出。
- 导出结果必须使用业务字段名和中文表头，不输出数据库密码、管理员 token、内部权限字段或无意义的系统字段。
- 导出内容必须区分主数据和翻译数据，能够再次作为合法导入模板使用。
- 对图片、PDF 和其他文件只导出文件名、业务标识或可访问链接，不把二进制文件混入表格导出。
- 导出行为必须受当前用户的数据权限约束，不能通过导出绕过角色权限。

#### 6.3.3 导入导出验收

- 运营人员可以下载产品和 FAQ 模板，填写后完成一次导入，不需要查看 UUID 或数据库字段名。
- 故意制造缺失必填项、错误语言、重复订货号、无效分类和错误关联时，系统能阻止或按明确模式处理，并返回可定位到原始行号的错误报告。
- 导入一批中英内容后，后台列表和前台对应页面能分别看到正确语言内容。
- 导出筛选结果后，导出文件可以在不改列结构的情况下再次导入。
- 无权限用户不能导入、导出自己无权访问的数据。

### 6.4 后台导航菜单配置

后台必须提供可配置的运营导航菜单，使不同岗位能够看到与工作职责匹配的内容入口。该能力只管理后台导航呈现，不改变集合权限、字段权限、发布权限或用户权限。

- 管理员可以新增自定义菜单项，配置菜单名称、图标、分组、排序和目标页面。
- 目标页面至少支持已授权的 Directus 集合列表页、集合编辑页、仪表盘或项目内已注册的后台扩展页面。
- 管理员可以编辑、隐藏、显示、排序和删除自定义菜单项，也可以对已有业务菜单进行显示顺序调整。
- 菜单名称支持中文，必要时支持英文或按后台当前语言显示；菜单名称不能要求运营人员理解集合名、表名或 UUID。
- 菜单可以按角色配置可见性，但角色看不到菜单不代表获得或失去数据权限；实际访问仍必须经过 Directus 权限校验。
- 系统核心菜单（用户、角色、权限、系统设置等）必须受到保护，不允许通过菜单配置删除其底层能力；是否隐藏由系统安全策略决定。
- 菜单目标失效、目标集合被删除或用户无权限时，后台必须显示明确的失效状态或不展示该入口，不得出现无提示的空白页。
- 菜单配置必须可随 schema snapshot、初始化脚本或后台配置备份一起恢复，不能只保存在某一台后台实例的浏览器缓存中。

#### 6.4.1 菜单配置验收

- 管理员可以新增“产品管理”“FAQ 管理”等业务入口，并拖动调整顺序。
- 隐藏或删除自定义菜单后，目标数据和权限不被删除；通过合法 URL 访问时仍按原权限执行。
- 不同角色登录后只能看到被配置为可见且本人有权限访问的菜单。
- 菜单配置导出、重建或恢复后，名称、分组、排序和目标页面保持一致。

### 6.5 第三方登录与外部平台配置

旧官网后台有微信登录配置，包括 AppID、AppSecret、登录及解绑回调地址、前台与后台独立启用开关；侧栏还存在其他第三方登录入口。上述界面只证明配置能力存在，不能据此认定各渠道仍在使用或全部需要迁移。

- 上线方案确定前，盘点各渠道的实际入口、近期开通和使用情况、用户量、绑定关系、应用归属、可用域名及回调限制，形成「继续支持 / 暂缓 / 停用」清单。
- 前台会员登录与后台管理员登录分别评估和启用。旧后台的开关状态不得直接转成新后台默认配置；后台管理员登录须另做安全评审。
- 对确认继续支持的渠道，明确登录、首次注册或绑定既有会员、重复账号处理、解绑、注销、授权失败和取消授权后的行为；迁移时不能因为同一第三方账号登录而误建第二个会员。
- 多语言独立域名下明确授权发起域名、回调域名、登录后的返回页及跨域会话方案。所有回调地址须在平台登记并使用 HTTPS，不能把旧 PHP 回调 URL 直接沿用到新站。
- 管理员可查看渠道名称、启用状态、应用标识和回调地址；敏感密钥仅允许授权人员设置或轮换，保存后不回显明文。配置修改、启停和轮换须有操作记录。
- AppSecret、私钥及访问令牌按环境隔离保管，不得写入前台资源、公开 Directus 集合/API、仓库、日志、导入导出文件或 schema snapshot；后台可配置体验不能以明文暴露密钥为代价。
- 不因旧后台出现微信、QQ、支付宝、Facebook、LinkedIn、Twitter 等菜单，就承诺全部渠道首期实现；渠道范围由盘点和业务确认决定。

#### 6.5.1 第三方登录验收

- 对确认上线的渠道，验证正常登录、首次绑定、既有会员绑定、重复账号、解绑、注销、授权拒绝、过期或错误回调，以及不同语言域名的返回路径。
- 未启用的渠道在前台无入口，且对应回调不能完成登录；后台管理员登录开关不影响前台会员登录。
- 普通编辑、前台访客、公开 API、导出文件和日志均无法取得密钥；授权管理员轮换密钥后，旧密钥失效且登录流程仍可恢复。
- 已迁移会员使用第三方登录后进入原会员账号，会员资料和下载权限不丢失。

### 6.6 逐页 GEO / SEO 配置与旧站承接

旧官网后台允许针对页面维护 H1、Title、描述、Schema 等信息。新官网应把这项运营能力落实到实际页面编辑流程，不能仅有前台自动生成代码，或只给部分页型建字段。迁移前先盘点旧站每种页面、语言和字段的实际数据、前台输出及可用性；只迁移有效内容，纠正现网错误，不盲目复制旧值。

- 每个可索引的公开页型都要有明确的后台编辑入口；内容页在该内容的语言翻译记录里编辑，固定页在该页面的语言配置里编辑。一个语言的修改不得覆盖其他语言。
- 每个公开内容翻译记录的 slug 在同一语言的编辑流程中可见、可编辑，并显示最终 URL 预览；新内容按 §4.6 从该语言标题生成初始值。已发布内容仅改标题时保持 slug 不变；主动改 slug 时必须预览并创建旧 URL 的 301 映射。
- 运营编辑区至少显示「页面 H1」「SEO 标题（Title）」「SEO 描述（Meta Description）」「结构化数据（Schema）」的中文名称、用途提示和预览入口；Title、描述与 H1 必须能单独修改，不强制三者相同。另提供当前语言、页面 URL、发布状态和负责的内容记录，避免找错编辑位置。
- Schema 首先由页型模板与已发布的结构化字段自动生成（如 Organization、WebSite、BreadcrumbList、CollectionPage、Product、Article、FAQPage 中适用的类型）；后台提供受控的结构化内容字段和经审核的覆盖/扩展入口，满足旧站按页调整的能力。普通运营不需要手填 JSON-LD；高级编辑需要使用时须有格式校验、类型/属性白名单、预览和发布权限，拒绝脚本或不受控 HTML。
- 后台应明确标注 Schema 自动字段与人工字段的来源和优先级。人工覆盖不得改错 canonical URL、产品订货号、页面语言、发布时间等事实字段，也不得输出与页面可见内容不一致的价格、库存、认证或参数。
- 未填写的 SEO 字段采用明确、可预览的回退：H1 用页面/内容名称，Title 用页型标题模板与名称，描述用该语言已发布摘要或经过审核的模板，Schema 用对应页型的真实数据自动生成。不能从另一语言静默回填，不能凭空生成产品事实；必要字段缺失时省略不成立的 Schema 属性。
- 对产品目录这类大批量页，允许先以可维护的页型模板批量生成，再对重点分类、系列和 SKU 逐条覆写。模板变量仅使用已验证数据，显示当前预览值和优先级，导入/导出保留逐条覆盖字段，避免要求运营手工填写所有订货号。
- 后台预览应展示页面最终 H1、`<title>`、Meta Description、canonical、hreflang、OG/Twitter 和 JSON-LD；保存、发布和缓存刷新后，可从对应语言域名的无 JS HTML 复核。草稿不得进入公开 sitemap 或公开 Schema。
- Schema 编辑、模板变更及批量导入应受角色权限、版本记录和审核流程控制；字段模型、中文控件、默认模板、校验与迁移脚本可从仓库重建。

## 7. 前台页面范围

### 7.1 页面类型

- 首页
- 产品中心
- 一级、二级、三级产品分类页
- 产品系列页
- SKU 产品详情页
- 新闻列表页
- 新闻详情页
- FAQ 列表页及 FAQ 详情/展开内容

- 下载中心

- 搜索结果页
- 会员登录、资料和下载页

### 7.2 页面通用要求

- 每个页面有明确语言。
- 每个页面有唯一 canonical。
- 每个页面按真实存在的语言生成 hreflang。

- 产品页必须显示真实订货号。
- 分类、系列、产品层级链接必须稳定。
- 内容缺失时有明确回退和 404 策略。
- 已发布页面的 H1、Title、Meta Description 与适用 Schema 必须按 §6.6、§8.4 的优先级输出，运营可从对应后台入口维护。

## 8. GEO / SEO 要求

### 8.1 必须具备

- `title`
- `description`
- canonical
- hreflang
- Open Graph
- Twitter Card
- JSON-LD
- robots.txt
- sitemap.xml
- llms.txt
- 404 页面
- 301 旧 URL 映射
- 产品、组织、新闻等结构化数据

### 8.2 多域名 GEO 规则

1. 每个语言域名只输出自身语言的 canonical。
2. hreflang 使用完整绝对 URL。
3. 中文站使用 `zh-Hans`，不是 `zh-CN` 作为 hreflang 主值。
4. sitemap 按语言域名输出真实可访问 URL。
5. 不把 staging、localhost 或内部 API 地址输出到生产页面。
6. 同一产品的语言版本要互相引用，缺失语言不虚构链接。

### 8.3 AI 可理解性

- 产品页输出清晰的型号、订货号、系列、分类和参数关系。
- 重要参数使用明确字段，不把关键内容只放在图片或 PDF 中。
- 页面正文避免大段无语义 HTML。
- 产品 JSON-LD 与页面真实内容一致。
- `llms.txt` 只列出真实发布页面。
- 页面必须支持 Googlebot、GPTBot、ClaudeBot、PerplexityBot 等无 JS 或有限 JS 抓取场景。

### 8.4 页型覆盖与字段优先级

以下是「逐页可编辑」的交付范围。表中的 Schema 类型为适用示例，须按实际页面内容判断；不能为了凑类型输出不存在的问答、价格、认证或产品信息。

| 页型 | 后台编辑位置 | H1 / Title / 描述 | Schema 基线 |
|---|---|---|---|
| 首页；关于、服务、解决方案、联系等固定内容页 | `site_pages` 对应页面及语言翻译 | 逐语言可覆写；未填按页面名/摘要回退 | WebPage；站点级 Organization、WebSite 按规则复用 |
| 产品中心及其他栏目首页；新闻、FAQ、下载列表页 | 对应栏目页配置及语言翻译 | 逐语言可覆写；支持列表页模板 | CollectionPage / BreadcrumbList，按实际内容补充 |
| 一级至三级分类页 | 分类语言翻译 | 逐分类、逐语言可覆写；可用分类模板 | CollectionPage / BreadcrumbList |
| 系列页 | 系列语言翻译 | 逐系列、逐语言可覆写；可用系列模板 | ProductGroup 或适用的页面类型 / BreadcrumbList；不虚构 SKU 属性 |
| SKU 详情页 | 产品语言翻译及产品真实结构化字段 | 逐订货号、逐语言可覆写；可用 SKU 模板 | Product / BreadcrumbList；字段与可见内容一致 |
| 新闻、FAQ、下载资料详情页 | 对应内容语言翻译 | 逐条、逐语言可覆写 | Article、FAQPage 或适用类型；仅基于真实正文/问答/文件 |
| 搜索结果、会员及系统页（404/500 等） | 站点级规则或必要的单页配置 | 具有合适标题与说明；按索引策略处理 | 不强制输出业务 Schema；搜索结果、登录及错误页按规则 `noindex` |

同一字段优先级为「该语言已发布的单页覆写值 → 该页型的语言模板 → 该语言真实内容回退」。输出时 HTML 可见 H1、`<title>`、Meta Description、OG 和 JSON-LD 应彼此一致但允许各司其职；`canonical`、`hreflang`、`robots` 和 URL 按站点语言/路由规则生成，其中内容页 URL 的 slug 必须取自对应语言翻译记录并遵守 §4.6，后台不能用任意文本覆盖破坏多域名关系。Schema 的站点级实体与页级实体应有稳定 `@id`，避免重复或冲突。

SEO 字段是否存在、后台控件是否可用和前台是否真实读取须逐页型对照验收。当前 demo 的 `site_pages_translations`、分类/系列/产品/新闻翻译已具备部分 H1、SEO Title 与 Description 字段，部分 Schema 由前台自动生成；这不等于所有 PRD 页型都已有后台编辑入口，也不等于 Schema 已可安全覆盖。

### 8.5 抓取说明文件的后台配置

- `robots.txt` 和 `llms.txt` 可从后台维护，但由前台按环境、域名和已发布内容生成最终文件，提供发布前预览、校验、版本记录与回退。
- `robots.txt` 使用受控规则配置：正式环境保留必要的系统保护规则；非生产环境强制禁止抓取，后台不得解除。规则按实际语言域名分别预览，防止误封首页、产品页或搜索引擎渲染所需资源。`robots.txt` 只管理抓取，不承担会员资料保护或页面 `noindex` 的职责。
- `llms.txt` 的各语言站点简介和精选链接可编辑；页面链接优先从已发布页面选择，输出时使用对应语言的真实域名，不收录草稿、会员页面或失效 URL。它属于补充性内容发现文件，不作为搜索效果保证。
- 普通运营不直接粘贴整份任意规则文本；高级编辑确需扩展时须经语法、目标 URL 和权限校验。发布后分别请求各语言域名的实际文件核对内容。

## 9. 部署方案

### 9.1 环境

| 环境 | 前台 | 后台 | 域名策略 |
|---|---|---|---|
| 本地 | Next.js 3000 | Directus 8055 | `/en`、`/zh` 路径模式，便于开发 |
| Staging | 1 套 Next.js | 1 套 Directus | 使用 staging 多语言域名 |
| 生产 | 1 套 Next.js | 1 套 Directus | 多语言独立域名 |

### 9.2 生产部署步骤

1. 阿里云 DNS 配置所有语言域名。
2. CDN 或负载均衡绑定所有域名。
3. 配置统一 HTTPS 证书或证书组。
4. 所有域名转发到同一套 Next.js 服务。
5. 配置语言域名映射和生产站点 origin。
6. 部署 Directus、MySQL、文件存储和搜索服务。
7. 导入 schema snapshot、权限、字段元数据和语言注册表。
8. 导入经过审核的数据和语言翻译。
9. 执行 sitemap、canonical、hreflang、机器人抓取和旧 URL 301 验收。
10. 切换 DNS 前保持旧站继续运行。

### 9.3 发布流程

```text
运营在 Directus 修改内容
        ↓
Directus webhook / 变更事件
        ↓
Next.js 按路径或 tag 增量刷新
        ↓
CDN 缓存刷新
        ↓
搜索索引同步
```

### 9.4 回滚

- 前台代码必须可以回滚到上一版本。
- Directus schema 变更必须有 snapshot 和备份。
- 数据迁移必须先 dry-run，再正式执行。
- 新站发布失败时，旧站保持可访问。
- 域名切换采用可回退的 DNS / CDN 配置。

## 10. 安全和权限

- 前台不得出现数据库密码、Directus 管理员 token 或 MySQL 连接代码。
- Directus 使用角色和权限限制编辑、发布、结构修改和用户管理。
- 生产管理员账号必须使用强密码和独立账号。
- 文件上传限制类型、大小和权限。
- 历史外链图片只允许来自明确白名单域名。
- 不允许通过前台参数任意代理外部 URL。
- staging 和生产凭据完全分离。
- 第三方登录密钥由受控服务端配置或密钥存储管理；后台配置页不得回显既有明文，密钥不得随公开内容 API、前台构建产物或配置导出泄露。

## 11. 验收标准

### 11.1 多语言域名

- 每个已启用语言都有独立域名。
- 所有语言域名访问同一套前台代码。
- 语言切换进入同一业务页面对应语言版本。
- 分类、系列、SKU、新闻、FAQ、下载资料和解决方案等公开内容详情使用其翻译记录中的可读本地化 slug；同一内容的中英文 URL 分别使用各自翻译 slug，符合 §4.6 的生成、唯一性和稳定性规则。
- canonical、hreflang、sitemap 使用正确域名。
- 不存在语言前缀和域名互相循环跳转。

### 11.2 后台

- 一个后台可管理所有语言。
- 分类、系列、SKU、新闻图片均支持完整图片操作。
- 没有 UUID 输入作为主要运营入口。
- 枚举使用中文下拉。
- 真实编辑页经过打开、编辑、保存、重新打开验收。
- 产品、FAQ 等列表支持模板下载、批量导入、筛选导出和错误报告。
- 导入导出遵守角色权限，不能通过文件或导出绕过权限。
- 管理员可以新增、隐藏、删除和排序自定义后台菜单，菜单不改变数据权限。
- 失效菜单目标有明确提示，菜单配置可随部署配置或备份恢复。
- 第三方登录渠道的启用状态、回调与密钥权限满足 §6.5；完成已启用渠道的账号绑定、解绑和跨语言域名回调验收。
- 前台会员登录、注册、找回密码及后台会员管理通过 §6.1.1 的真实账号和迁移验收；未通过不得整体替换旧官网。
- 后台只有一套前台会员列表；同一会员从中英文站登录、修改资料和下载后，后台仍对应同一会员记录，会员组和下载记录一致。旧站跨语言重复账号须按经核实的规则合并或标记待处理，不得静默覆盖资料。
- 首页 Banner 在后台按推广内容显示一条记录，打开后可编辑中英文；调整顺序、发布状态、图片和业务跳转目标后，两种语言前台均按各自内容正确展示。缺失或未发布的语言内容不显示另一语言文案。
- §8.4 中每个已交付公开页型都能从明确的后台入口分别修改中英文 H1、Title、描述，并看到最终预览；修改一个语言不影响另一语言。
- 重点页可编辑 Schema 内容；普通运营通过受控字段修改，高级覆盖经过校验和审核，错误 Schema 无法发布。

### 11.3 前台

- 主要页面在所有已启用语言域名返回 200。
- 不存在内容返回正确 404 或明确回退。
- 产品详情显示订货号和关键参数。
- 图片、PDF、下载链接权限符合要求。
- 会员可以使用已迁移账号登录并维护资料；新注册、找回密码和退出登录流程可用。
- 同一个会员账号可在中文站和英文站使用，账号资料与下载权益不因切换语言而分裂；不同顶级域名间的自动登录体验按最终会话方案验收。
- 移动端、平板、笔记本和大屏无明显重叠、溢出和遮挡。

### 11.4 GEO / SEO

- 生产环境不输出 localhost、staging 或内部 Directus 地址。
- 所有页面 title、canonical、hreflang、结构化数据可被无 JS 抓取。
- sitemap 只包含真实存在的公开 URL。
- 旧 URL 301 映射经过冲突审计。
- 抽查中英文新闻详情：英文 slug 由英文标题按规则生成，中文 slug 保留标题汉字并清除特殊符号；修改已发布标题不会改变 URL，主动修改 slug 会将旧 URL 301 到新 canonical URL。
- 以旧 ID、订货号或历史 slug 访问公开详情时，301 到对应语言的当前 slug URL；语言切换定位同一内容的目标语言翻译 slug；不存在或未发布的目标内容返回 404，不能输出错误 hreflang 或将用户送到无关页面。
- 抽查首页、栏目、三级分类、系列、SKU 和新闻详情的中英文页面：后台修改 H1/Title/描述及适用 Schema 后，发布页无 JS HTML 与预览一致；留空按 §8.4 回退，缺失或草稿语言不产生错误的 hreflang、sitemap 或 JSON-LD。
- Schema 通过 JSON 解析和适用类型校验；产品订货号、语言、图片及其他事实属性与页面内容一致，未确认数据不输出。

## 13. 开发原则

- 先确认数据模型，再做后台页面。
- 先写失败验证，再实现功能。
- 每开发一个后台能力，必须完成真实 Directus 页面验收。
- 每开发一个前台页面，必须检查中英文及其他启用语言。
- 不因旧站有多套语言项目，就复制新项目。
- 不把原始 URL、UUID、内部枚举值直接暴露给运营人员作为主要操作方式。
- 导入导出必须使用业务字段和模板，不允许用批量文件绕过权限或直接写数据库。
- 菜单显示配置与数据权限分离，隐藏菜单不能被当作权限控制使用。
- 不把图片能加载当作图片编辑体验完成，必须同时检查位置、间距、遮挡、空状态和窄屏布局。
- 每个阶段完成后更新进度文档和验证命令。
- GEO/SEO 能力按页型同时交付后台编辑、默认回退、前台输出和无 JS 验收；不得只新增字段或只在代码中拼接 Schema 就标记完成。

## 15. 结论

新官网采用“独立语言域名 + 一套前台代码 + 一个 Directus 后台 + 一个统一数据模型”的方式建设。

它能够保留现有官网每种语言独立站点的用户体验，同时消除旧系统多套 PHP 项目带来的重复开发和维护成本。

正式开发前，最重要的不是继续堆页面，而是先冻结：

1. 语言清单；
2. 域名清单；
3. 翻译数据模型；
4. 后台能力对照表；
5. 迁移和回滚方案。

上述五项确定后，再扩展技术参数、下载、认证、会员和产品选型等复杂模块，后续返工风险会明显降低。

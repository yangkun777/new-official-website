## 1. 项目背景与问题定义

### 1.1 现状（实测）

- **技术底座**：PHP 5.6.40（EOL）、Apache/Tengine、MySQL 5.7 / 阿里云 PolarDB
- **生产数据**：单库 `db_degson_all`，`hr_article` **4,385,755 行**（另测：product 频道行 147,250，系列码去重约 3,900）
- **发布模型**：全静态生成（`hr_category.sethtml` 183 行全为 1），内容变更需人工分批重生成十几万页面
- **代码组织**：页面逻辑散落三处——模板文件 + **库内 109 条 `hr_tags` 片段**（含 SQL 与 HTML）+ 185 条字段配置；无版本控制
- **数据模型**：`hr_article` 103–106 列通用字段池（text1–26/description1–10/thumb1–9）；多语言为"每语言一份完整行"（13 份副本），外语产品描述实测 **96.9–97.7% 为英文逐字副本**
- **后台**：225 个菜单项中 101 项停用；近 90 天实际操作账号 **仅 1 人**
- **安全隐患**：代码树含 root 级库凭据明文（`xhr/Conf/config.php` 的 `DB_CONFIG2` 及 4 份备份）、网站根目录存在改名 Adminer（`t3D3XGeAZ2QY3wUF.php`，403KB）
- **"加字段"的真实代价**：GEO 改版加 description 字段 → `hr_category` 增 **16 个语言列**（膨胀至 158 列）；填写率英文 13/183、**其余语言全部 0/183**
- **GEO 改版现状（本版重新实测，纠正 v1.6 的乐观表述）**：见 §7.2 第 9 条附。**残余缺陷不止 `<html lang>` 与 productlist20 空 H1**，另有 canonical 指向 404、hreflang 指向错误站点、新闻页挂错文章 Schema 等 4 类硬伤

### 1.2 核心问题（按痛点排序）

1. **多语言是第一痛点，痛在工程与运营两头**：每个语言站是独立 PHP 项目（同功能写 N 遍）；运营发一条内容要按语言分别上传（×13）；连"加一个后台字段"都要付出结构代价（16 语言列）
2. **供应商黑盒，无法自主**：取数逻辑在数据库里，无版本控制、无 diff、无 review；GEO 改版本身就在证明这一点——每改一项都要供应商在服务器上手工改模板
3. **GEO/SEO 改进流程不可持续**：前端项经改版已改善，但真实成本在流程——每新增一个 SEO 能力 = 改 schema ×16 语言列 + 改 N 套代码树 + 人工重生成静态页，三项都是按次收费的手工活。**且现网改版产出本身存在硬伤（§7.2 附）**
4. **运行时无安全补丁**：PHP 5.6 + ThinkPHP 3 无升级路径，叠加明文凭据与根目录 Adminer
5. **数据资产缺约束**：订货号/系列码无唯一约束（实测各 3 例重复），参数沉睡在通用字段池

### 1.3 项目动机

公司侧：摆脱供应商依赖、降低长期成本、GEO 能力自主。
实施侧：建立"有文档、有决策记录、别人能接手但内部最懂"的自主可控系统。

## 5. 总体架构需求

### 5.1 技术栈（本版修订：后台锁定 Directus 11）

| 层 | 选型 | 替代旧系统的什么 | 决策依据 |
|---|---|---|---|
| 内容后台 | **Directus 11（版本锁定）** | 供应商 PHP 后台（225 菜单黑盒） | 数据库优先、无代码侵入；界面加字段/改显示名满足内容与定义可配；无写 SQL/HTML 进库的入口；translations 机制原生匹配"主数据+翻译行"。**不选 12：12 引入主动许可执行，超 Core 额度会阻断 `/items` API 并禁止非管理员登录——生产站有被锁死风险** |
| 数据库 | **MySQL 8.0**（生产最终 PolarDB MySQL 8 兼容版） | MySQL 5.7 通用字段池 | 4.39M 行同方言搬运而非跨方言翻译；参数为三级关系树不需 JSONB |
| 前台 | **Next.js 15（App Router）+ TypeScript + ISR** | PHP 模板 + 静态生成 | 按需 revalidate 替代人工重生成；metadata/JSON-LD/hreflang/sitemap 代码生成 |
| 搜索/筛选 | **Meilisearch** | 旧站无独立搜索（`hr_search` 14,410 条证明有真实需求） | 毫秒级筛选（极数/间距/连接方式）、多语言分词开箱 |
| 部署 | 阿里云（ECS + CDN，延续现有云资产） | 现有 Tengine + 静态页 | 不换云；静态产物继续吃 CDN |

> **Directus 版本策略**：`package.json` 使用**精确版本**（不带 `^`），并在 §5.4 记录锁定值与升级流程。**升级前必须在 staging 验证**，且需评审许可条款变化。

### 5.2 数据流

```
编辑 → Directus 后台（写 MySQL 8）
         │ 内容变更触发
         ▼
     Webhook → Next.js 按需 revalidate（仅受影响路径，按 tag）
         ▼
前台（Next.js，读 Directus REST/GraphQL API）→ CDN
搜索索引：Directus 变更 → 同步任务 → Meilisearch
```

**硬性约束**：
1. **前台不直连数据库**。验收含代码扫描：`web/src` 内不得出现 `mysql2` / `DB_PASSWORD` / `createPool`
2. 生产库 `db_degson_all` 全周期**只读**（迁移源），所有写操作只发生在新库
3. 所有配置与代码进 Git；schema 变更走 Directus snapshot + diff（§5.4）

### 5.3 环境矩阵

| 环境 | 用途 | 数据 |
|---|---|---|
| 本地开发 | 开发自测 | 本地 MySQL + 种子（M0.2 已备：60 系列 / 378 产品） |
| Staging | 验收、迁移演练 | 生产数据只读导出的副本（脱敏凭据） |
| 生产 | 上线 | 新库；切换前旧站保持运行 |

### 5.4 底座与可复现性（★ 本版新增，验收级）

> **背景**：实测 M0.2 试点发现，仓库**无法重建后台**——`directus_fields` 只注册了 news 的字段，`category`/`series`/`product` 为 0；**没有任何 schema 快照**；`02_schema_clean.sql` 声明 `utf8mb4_unicode_ci` 而实库为 `utf8mb4_0900_ai_ci`（因 DDL 只写 `DEFAULT CHARSET=utf8mb4` 未写 `COLLATE`，落到 MySQL 8 的 charset 默认值）。
> **要求**：底座期必须先解决"可复现"，否则后续每加一个功能都在加深不可逆依赖。

| # | 要求 | 验收标准 |
|---|---|---|
| R1 | **删库可重建** | 清空 `degson_pilot` → 按仓库内文档与脚本重建 → **后台与重建前逐项一致** |
| R2 | **Directus 快照进版本控制** | 导出的 schema 快照文件（集合/字段/关系/权限/角色/语言）随代码提交；每次结构变更同步更新并 review |
| R3 | **版本精确锁定** | Directus、Next.js、Meilisearch 等在 `package.json` 写**精确版本**；升级走 staging + 评审 |
| R4 | **collation 全库统一** | 选定**一种** collation 写入 DDL 与文档，每个 `CREATE TABLE` 显式声明 `COLLATE`；`directus --help` 不再报 collation 警告 |
| R5 | **旧库底料与新模型分库** | 旧库底料（`hr_article`/`hr_category`）独立存放，只读参照；新库只含新模型 + `directus_*` |
| R6 | **凭据零入库** | 全仓扫描零命中；`.gitignore` 覆盖所有凭据文件与令牌 |
| R7 | **底座自检脚本** | 数据模型自检 + 多语言回退自检 + SEO 产出自检，可一键运行并给出期望值 |

> **R4 建议值**：`utf8mb4_0900_ai_ci`（MySQL 8 的 utf8mb4 默认值）。理由：Directus 界面建表落到该 collation，手写 DDL 显式声明同值即可全库一致，避免 JOIN 时 `Illegal mix of collations`。
> **R5 现状**：已完成拆分（`degson_legacy` = hr_article 16,744 + hr_category 183）。

### 5.5 取数模式（★ 本版修订：已实测完毕，结论为 REST）

**M0.2 README 记录**："本 Directus 对深层 filter（`filter[rel][field]`）报 403、M2O 字段展开返回空"，故改用"两次 root 查询 + 应用层 join"。

**M0.3 实测结论：该记录不成立。** 逐级验证结果（Directus 11.17.4）：

| 方式 | 结果 |
|---|---|
| REST 单表字段 `fields=id,title` | ✅ 200 |
| REST M2O 裸字段 `fields=series_id` | ✅ 200 |
| REST M2O 点号展开 `fields=series_id.id` | ✅ 200 |
| REST M2O 通配展开 `fields=series_id.*` | ✅ 200（返回完整嵌套对象） |
| REST 关系过滤 `filter[series_id][matecode][_eq]=…` | ✅ 200 |
| REST 三级关联过滤 `filter[series_id][category_id][level][_eq]=3` | ✅ 200 |
| REST 遍历翻译行 `fields=translations.language,translations.name` | ✅ 200 |
| GraphQL 嵌套展开 / 关系过滤 / 遍历翻译行 | ✅ 200 |

**403 的真实来源**：早期测试是用 PowerShell `Invoke-WebRequest` 直接拼 URL，其中的 `[` `]` 被 PowerShell 当作**通配符**处理，导致请求异常——**是测试工具自身的问题，不是 Directus 的限制**。改用 Node `fetch` 逐级重测后全部 200。

**同时发现并修复了一个真实的模型缺陷**：首次建模只建了 M2O（`product_translations.product_id → product`），**父表上没有反向 O2M 别名**，导致
- GraphQL 报 `Cannot query field "product_translations" on type "product"`
- Directus「语言页签」也无法工作

**已补齐**：四个父集合各增一个 `translations` 别名（`special: o2m`），并将 `directus_relations.one_field` 指向它。补齐后 REST 与 GraphQL 都能遍历翻译行。

> ⚠️ **踩坑记录**：Directus 11.17.4 的 `PATCH /relations/<collection>/<field>` 会崩溃
> （`RelationsService.alterType` 读 undefined 的 `schema.collections[...]`，服务直接挂掉，实测两次）。
> **别名字段用 `POST /fields` 建；`one_field` 改为直接写 `directus_relations` 表（停服务后改，再重启）。**

**结论（取数模式定案）**：
1. **前台取数走 REST**，包括关系过滤与嵌套展开；**不需要"两次查询 + 应用层 join"** —— 该绕法在 4 万 SKU 规模会失效，现在可以彻底放弃
2. GraphQL 同样可用，作为备选；需要遍历翻译行时依赖上述 O2M 别名
3. 前台仍**不直连数据库**（§5.2 硬性约束不变）

### 6.4 多语言取数与回退（SKU 页场景）

1. **存**：`product` 主表一条（订货号/参数/图纸，语言无关）+ `product_translations` 每语言一行
2. **取**：前台按 URL 语言解析语言码，一次请求取"主数据 + 对应语言翻译行"
3. **回退**：请求语言缺失或字段为空 → 回退 `en` 值渲染，后台标记"该条未翻译"；**绝不把英文复制为翻译值**
4. **hreflang**：同一主数据下**已有翻译行**的语言自动互链；**未翻译的 SKU 不生成对应语言页**（避免空壳页），列表页标注"该产品暂无中文页"并链接英文页

**语言码规范（本版统一）**：**`en` / `zh` / `de` / `es` / `fr` / `ja` / `ko` / `it` / `pl` / `hu` / `cs`**（两位短码，全站单一来源）。
> 用于：URL、数据库 `language` 字段、hreflang、`*_translations` 唯一性 scope、Directus languages 集合。**不得混用 `en-US`/`zh-CN`。**

### 6.5 URL Slug 策略

| 实体 | slug 规则 | 是否分语言 | 理由 |
|---|---|---|---|
| **product（SKU）** | **slug = 订货号**（如 `/product/DG271V-2-102`） | 否，各语言同 URL | 订货号语言无关且全球唯一；外部引用链接永不因翻译变化 |
| category / series / news / solution / page | 翻译行内 `slug`，每语言独立可编辑 | 是 | 母语 slug 是各语言站排名因素 |

**slug 生成规则**（架构期约定，slug 值逐条可改）：en 用 kebab-case；zh 默认**拼音全拼**（如 `chabashi-duanzi`），允许改为中文原文；`(实体, 语言, slug)` 组合唯一；改 slug 自动 301；旧 URL 的 id 不进新 slug。

### 9.2 新架构语言策略

- 语言 = 翻译维度，不是站点维度
- 上线分三批：**第一批 en + zh**（跑通全链路）；第二批按流量裁决（de/es/fr 候选）；第三批其余
- **站点减法**：cs（空 sitemap）等名存实亡站点建议停用并 301 到 en

### 9.3 翻译质量治理

迁移时外语站"英文副本"**不迁移为翻译**，标记"未翻译"（回退英文显示），避免把假翻译带入新系统被判定 doorway/duplicated；分类名等已有真翻译照迁。

## 12. 数据迁移（最大风险项，难度 4/5 星）

### 12.1 迁移源与方式

源：`db_degson_all`，**全程只读账号**，禁止用历史 root 凭据。
方式：只读导出 → ETL 清洗 → 新 schema 播种。每批出**迁移报告**（源行数 vs 目标行数、丢弃明细及原因）。

### 12.2 迁移范围（★ 部分量级需复核）

| 批次 | 内容 | 量级 |
|---|---|---|
| P1 | 产品目录全量（系列 3,614 / 订货号 13,098 / 全语言变体） | ⚠️ **需复核**：v1.6 记"约 4 万+行"，本版实测 `catid=552` 全语言 **147,250 行**（差 3.5 倍），直接影响工时 |
| P2 | 分类树（183 行）+ 分类名真翻译 | 小 |
| P3 | 新闻（公司新闻 catid=472：cn 350 / en 85 / gz 9 / 其余各 ≤4；新品通讯 catid=13：cn 10 / en 10 / de 7 / ru 7 / es 6 / fr 6） | 小（共约 470 行） |
| P4 | 下载附件 + 媒体 URL 改写 | 中（媒体量待盘点） |
| P5 | 单页/about 内容 + `hr_tags` 内容物抽取进 site_settings | 中 |
| P6 | 会员账号全量（4,334 人：资料 + 旧密码哈希） | 小 |
| 不迁 | 问卷历史（仅归档）、外语站假翻译正文 | — |

**P3 专项：旧新闻多语言配对**（旧库无显式关联键；用 `同 catid + id 相邻(±5) + 时间窗(±1天)` 自动生成《配对候选表》→ 人工核对约 470 行 → 配对成功者主数据 + 各语言翻译行；未配对者按单语言迁入，翻译行留空待补）

### 12.3 `hr_tags` 109 条片段处置

逐条判读 → ①纯文案 → site_settings/字段；②取数逻辑 → 代码组件；③废弃死片段（32 条）。产出《片段→组件映射表》为验收物；**未判读完不得进入 M2**。

### 12.4 已知数据瑕疵（迁移必须裁决）

| 瑕疵 | 实测 | 处置 |
|---|---|---|
| 重复订货号 | 3 例（如 `21010000001` 挂两个系列） | 业务裁决归属；新库唯一约束上线前解决 |
| 重复系列码 | 3 例（分类 231583 内） | 同上 |
| 空 thumb / 双域图片 URL | 普遍 | 统一改写 + 默认占位图 |
| catid=554/555（约 2.6 万行 title 为空） | 身份待查 | 迁移前判读 |
| `updatetime` 为 Unix 秒 | 全表 | 转 ISO 8601 |
| **collation 不统一** | 旧库 `utf8_general_ci`，新库须统一（§5.4 R4） | 迁移时显式转换 |

### 12.5 URL 与 301

旧 URL 形态（`/product/classify20_231580.html`、`/content/details_552_4409209.html` 等 53 条规则）→ 新 URL 全量映射表；301 以边缘层（CDN/Nginx）+ 应用层双重兜底；映射表进 Git；**旧站 sitemap（en 13,477 页）覆盖率必须 100%**。

### 13.6 实测发现的额外风险项（本版新增）

| # | 风险 | 说明 | 处置 |

| X1 | **collation 混用** | 实测新模型表为 `utf8mb4_0900_ai_ci`、旧库底料为 `utf8_general_ci`、DB 默认 `utf8mb4_unicode_ci`；Directus 启动即报警告。根因：DDL 只写 `DEFAULT CHARSET=utf8mb4` 未写 `COLLATE` | §5.4 R4 统一 |

| X5 | **源文件编码** | 部分源文件注释在 PowerShell 下显示乱码（UTF-8 被按 GBK 读），属读取侧问题；但**写入侧若用 PowerShell `ConvertTo-Json` 拼中文会存成 `????`**（试点已踩） | 统一 UTF-8 无 BOM 写入；中文内容走 SQL 文件或界面 |

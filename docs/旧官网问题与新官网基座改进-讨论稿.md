# DEGSON 旧官网问题与新官网基座改进（老板汇报讨论稿）

> 日期：2026-10-23  
> 用途：确认后再制作 Excel。  
> 范围：综合旧站实测报告、`E:\degsonen\degsonEn` 旧站文件和线上页面；中文站 GEO 暂不纳入本次问题清单。

## 建议先向老板说明的核心结论

官网不应只被看作一个展示页面，而应像公司的 **OA、CRM** 一样，作为长期使用的企业数字化基础设施建设。

过去官网的核心代码、数据结构、发布方式和问题处理长期依赖外部供应商。公司提出需求后，需要在线反复沟通；即使是简单修改，也可能进入单独报价、排期和验收流程，成本高、响应慢，公司内部缺少主动权。

新官网项目的核心目标之一，是把**代码、数据、账号、部署、文档和持续迭代能力掌握在公司自己手里**。由内部团队主导建设和维护，供应商只作为必要的补充资源，避免官网继续形成长期外部依赖。

## 按优先级排列的问题清单

> **截图标记**：`【可截图｜旧站前台】`、`【可截图｜旧站后台】` 表示可直接从对应页面截取；未标记的痛点需要用沟通记录、代码/数据库实测或其他项目材料佐证。

| 之前官网存在的问题 / 痛点 | 证据或截图 | 新官网基座如何解决 |
|---|---|---|
| **P0-1｜官网核心能力长期掌握在供应商手里。** 公司内部没有完整掌握代码、数据结构、部署和故障处理方式，普通维护也依赖原供应商。人员或供应商变化后，官网持续运营存在风险。 | 葡语站开发评估把供应商列为最大卡点，并要求移交生产代码、数据库、OSS、发布流程和云账号权限；旧站仍有多个数据库和环境用途无法确认。 | **新官网按内部自研项目建设。** 核心代码、数据库、CMS、账号、部署脚本、文档和验收标准由公司持有，像 OA、CRM 一样形成内部长期能力；外部供应商只承担必要的专项工作。 |
| **P0-2｜沟通和报价成本高。** 需求只能通过线上与供应商沟通，业务人员和供应商对页面、字段、数据的理解经常不一致，需要多轮解释；简单的小需求也可能单独报价，费用高、排期长。 | 内部评估显示新增一个葡语站约需 11 周，其中约 3 周是等待供应商交付；内部报价预估为 4.5–5.5 万元、28 人日，并提示源码和部署链可能形成锁定溢价。实际小需求可再补 2–3 个聊天和报价案例。 | **内部团队可直接处理日常需求。** 文案、图片、页面板块、产品数据和基础样式通过后台或内部代码完成，不再为每个小修改向供应商询价；较大需求也能先由内部明确方案和工作量。 |
| **P0-3｜旧系统结构复杂，问题难定位。** 旧官网按语言拆分为独立 PHP 项目，各语言站点分别维护代码和发布链；同时存在两代 CMS、多个历史环境和 15 个生产数据库。发生问题时需要跨项目、语言站、数据库及静态文件定位，也容易出现责任边界争议。 | 实测有 12 个“一语言一库”站点、15 个生产数据库；旧站目录中可核对各语言独立 PHP 项目；`ko`、`pl` 实际是多语言主库，`gw` 等用途仍需确认。 | **统一为一个技术基座。** 一个 Next.js 前台、一个 Directus 后台、一套主数据和统一部署流程；代码、数据模型、项目说明和验收脚本集中管理，问题可以快速分层定位。 |
| **P0-4｜技术栈陈旧，长期维护风险高。** 旧站使用 PHP 5.6、ThinkPHP 3 系和自研 CMS，安全维护、现代工具兼容、招聘接手和系统升级都越来越困难。 | 实测 PHP 5.6.40；PHP 5.6 已于 2018 年停止官方支持。 | **已建立现代化基座。** 使用 Next.js 15、TypeScript、Directus 11 和 MySQL 8 方向，前台、后台与数据接口分层，便于公司内部培养和补充维护人员。 |
| **P1-1｜多语言内容需要重复上传。** 每种语言长期对应不同项目和数据库；同一条新闻需要进入每个语言后台分别上传，产品和页面修改也要重复操作，容易漏传、错传和版本不一致。 | **【可截图｜旧站后台】**同一条新闻在不同语言后台分别创建/上传的入口；也可截各语言页面的发布时间差异。12 个“一语言一库”站点的数据结构需用调研记录佐证。 | **一条内容集中管理多种语言。** 新闻、产品和页面只建立一条主记录，各语言文案在同一记录的翻译区维护，共用图片、发布时间和发布状态。 |
| **P1-2｜后台不好用，依赖经验。** 产品实际上被当作“文章”管理，大量字段叫“备用文本框”、`text3`、`text18`；同一个字段在不同栏目里还可能代表不同业务含义。 | **【可截图｜旧站后台】**重点截产品编辑页，展示“文章”式编辑和备用字段。文章模型实测 102 个通用字段、`text3` 至少有 6 种含义，需调研记录佐证。 | **后台按业务重新建模。** 分类、系列、产品、规格、媒体、附件、认证和关联产品分开管理；使用中文标签、字段说明、分组、图片预览和固定选项下拉。 |
| **P1-3｜产品数据重复且存在脏数据。** 同一产品在不同语言和辅助表中大量重复，语言字段还存在空值、空格和中文名称混用，后续维护和统计困难。 | **【可截图｜旧站后台，视权限与数据可见性】**如后台可查看产品语言字段，可截空值、空格或中文语言名记录；438 万余行、约 3,906 个去重料号及 35 种语言值仍以数据库统计作为证据。 | **统一产品身份和语言标准。** 按订货号维护唯一产品主记录，统一语言码；全量迁移时生成重复、缺失和冲突清单。 |
| **P1-4｜技术参数和产品关系难维护。** 参数、配套产品、认证、对配产品和近似产品被压成特殊字符串，不利于修改、校验、筛选和复用。 | **【可截图｜旧站后台】**如产品编辑页可见原始参数/关系字段，可截取对应字段；字段包含 `\|tech\|`、`\|PW\|`、`\|PH\|` 等编码，产品关系也保存为组合字符串。 | **部分落地：**使用结构化规格和标准关系字段；正式建设时完成全量参数、关系和筛选规则迁移，为产品搜索和选型打基础。 |
| **P1-5｜产品发布非常慢。** 即使只修改一个产品，也需要重新发布整个产品模块的 13,000 多个产品页面，通常要等待数小时；发布过程中还难以快速确认哪些页面已经更新。 | **【可截图｜旧站后台】**截“生成静态 / 批量生成”界面及任务数量；13,000 多页、耗时数小时最好同时保留真实任务记录或起止时间作为佐证。 | **只更新受影响的页面。** Next.js 按页面生成并使用缓存，修改一个产品只影响对应产品及关联页面，不再全量重发整个产品库。后台保存后即时精准刷新的能力将在正式阶段接入。 |
| **P2-1｜产品导航和搜索效率不高。** 顶部产品菜单一次展开大量分类和子分类，用户很难快速定位目标；旧数据结构也不利于按型号、间距、极数等条件筛选。 | **【可截图｜旧站前台】**截顶部产品菜单展开状态；也可录屏从首页查找一个具体型号的操作路径。 | **先收敛入口，再逐层选型。** 新前台按核心产品族组织导航，产品页分层浏览；后续接入 Meilisearch 和结构化参数筛选。 |
| **P2-2｜页面视觉和交互已显陈旧。** 首页轮播较多、内容重复，固定顶栏、底部菜单和在线咨询长期占用空间，品牌重点不够集中。 | **【可截图｜旧站前台】**[旧官网首页截图](./evidence/old-site-home-2026-10-23.png)；可补首页中段和移动端截图。 | **演示版已重做。** 采用白底工业目录、品牌红、高清产品图、自动轮播、拖拽切换、视频循环、滚动入场和悬停反馈，并统一主要内页风格。 |
| **P2-3｜历史代码和版本文件混乱。** 同时存在 `xhr`、`xhr20210826`、`statics20210826`、备份目录和多份日期样式文件；首页还混合大量脚本、插件和行内样式，修改容易产生连锁问题。 | 本地目录可直接截图；旧首页约 98KB，包含 31 个脚本、9 个样式表和 52 处行内样式。 | **统一 Git 和组件化开发。** 历史版本通过提交记录追踪，公共功能复用组件；TypeScript 和自动检查降低改动风险，不再依靠复制目录保存版本。 |
| **P2-4｜缺少统一交接和验收标准。** 系统知识集中在供应商和少数熟悉历史规则的人手里，问题修复往往依靠个人经验，难以确认其他语言和页面是否同步解决。 | 可补交接资料缺失、同类问题重复出现或需要供应商确认的案例。 | **持续沉淀内部知识。** 新项目维护项目总况、交接文档、数据脚本和自动验收脚本，配置随代码版本管理，减少对个人和单一供应商的依赖。 |
| **P2-5｜公网官网与内部系统入口混在一起。** 官网顶部直接提供 OA 入口并指向内网地址，普通访客无法使用，也把内部系统信息暴露在公共页面上。 | **【可截图｜旧站前台】**截首页顶部 OA 入口；链接目标 `192.168.10.10:8080` 可通过鼠标悬停或复制链接地址佐证。 | **分清公共官网与内部系统边界。** 新官网只保留客户和公开业务需要的入口；OA、CRM 等内部系统通过公司内部门户、VPN 或统一身份入口访问。 |

## 建议优先准备的截图和材料

1. **供应商沟通与报价案例**：简单需求、多轮沟通、报价较高各选一个典型案例。
2. **旧后台产品编辑页**：突出备用字段、长表单和难理解的操作。
3. **旧首页与新首页对比**：使用相同分辨率截取首屏和产品内容区。
4. **旧站产品大菜单**：体现信息过密和查找路径长。
5. **旧后台批量生成静态页面**：体现发布流程复杂。
6. **历史项目目录**：`xhr`、`xhr20210826`、备份目录和多份日期样式文件。
7. **新闻多语言重复上传**：同一条新闻在两个语言后台的编辑页面。
8. **单产品修改后的全量发布**：任务数量、开始时间和完成时间。
9. **公共页面的 OA 内网链接**：顶部 OA 入口及其 `192.168.10.10:8080` 地址。

## 汇报表述建议

- 不把重点只放在“技术升级”，而是强调：**官网核心数字资产回归公司掌控，降低长期供应商依赖和持续采购成本。**
- 对老板可直接表达为：**新官网不是重新买一套网站，而是在公司内部建立一套可以长期迭代的网站能力。**
- “已落地”只代表当前基座已完成并验证的能力；搜索、全量迁移、全量媒体搬迁和保存后即时刷新仍属于后续建设。
- 不在材料中展示数据库账号、服务器路径、生产连接信息或个人联系方式。

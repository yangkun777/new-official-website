# 多语言 SKU 产品官网：成熟方案调研与基座复评

日期：2026-10-20。范围：工业连接器类「官网型产品目录」——页面少、SKU 多、多语言、会员受控资料。对照物：`D:\degson-pilot` 当前 Next.js + Directus + MySQL 基座。本文是公开案例与行业分层对照，不是压测报告，也不是选购招标书。

## 结论

**高松这类站，行业里流行且靠谱的做法不是「买一个能管一切的 CMS」，而是分层：产品主数据一层、营销内容一层、搜索索引一层、前台一层、会员/下载一层。** Next.js 做前台、关系库存产品与翻译、独立搜索、独立鉴权，是 2024–2026 制造商官网/产品门户里最常见的组合之一。

**当前基座方向与这个分层一致，可以继续。** Directus 在业界也确实被用来同时管内容和产品（有落地案例），但正规用法是把它当编辑后台和 API，而不是搜索引擎、不是下载网关、不是会员会话服务。1.3 万订货号属于「大目录官网」，远未到必须先上 Akeneo/Pimcore 才能做站的规模；菲尼克斯那种 PIM + ECLASS + BMEcat 是多渠道工业数据分发，不是「先建官网」的门槛。

不必现在换栈。缺的是分层里还没落地的几块（搜索、属性字典、受控下载、生产对象存储），不是 Next 或 Directus 选错了。

## 先把「流行正规」拆开

容易混在一起的三类站：

| 类型 | 典型目标 | 常见技术重心 |
|------|----------|----------------|
| 消费品电商 | 下单、库存、促销 | 商城引擎 + 支付 |
| 工业制造商官网 | 找产品、看参数、下资料、询盘 | 目录 + 筛选 + 多语言 + 文件权限 |
| 工业数据枢纽 | 同一套资料喂官网、经销商、CAE、打印目录 | PIM + 分类标准 + 渠道输出 |

高松现在接近第二类，PRD 里的独立域名和 GEO 仍是「一个产品库、多个前台入口」，还不是菲尼克斯那种全渠道数据产品。选型时应对标制造商产品门户，而不是 Magento/Shopify，也不是一上来对标集团级 MDM。

「正规」在这类项目里通常指：

1. 产品事实和营销文案分开管，产品页由两者拼出来。
2. 搜索不打主库，打派生索引。
3. 公开页可缓存；登录、价格、下载实时校验。
4. 文件不靠猜 URL 就能拿走。
5. 产品有稳定 ID、语言行、属性有定义，而不是每篇 SKU 一篇自由 HTML。

这与 MACH/可组合架构的表述一致：PIM 管规格、变体、翻译、资源引用；CMS 管栏目和运营页；二者重叠在产品页。[PIM 与 CMS 的分工](https://pimvendors.com/knowledge-base/core/headless-and-composable-commerce-pim)

## 行业里实际在用的栈（按层）

没有唯一「标准产品包」。公开案例反复出现的是同一套层，产品名可以换。

| 层 | 职责 | 常见产品 | 当前基座 |
|----|------|----------|----------|
| 前台 | 路由、ISR/SSR、SEO、页面拼装 | Next.js 最常见；也有 Nuxt | **已有 Next 15** |
| 内容 CMS | 首页、新闻、方案、关于、块编排 | Storyblok、Sanity、Statamic、Strapi、Directus、Pimcore Documents | **Directus 11** |
| 产品主数据 | 系列/SKU、属性、多语言、资料引用 | Akeneo、Pimcore、或 CMS 里的结构化表 | **MySQL + Directus 编辑层**（产品表已建） |
| 搜索 | 全文 + 分面（极数、间距、分类） | Algolia、Meilisearch、Azure Search、ES | **M2 未落地** |
| 资源 | 图、PDF、CAD；权限与派生格式 | DAM / OSS；Cloudinary、Canto、S3/OSS | **试点走 Directus assets，非生产拓扑** |
| 身份与下载 | 会员、授权、审计、短时链接 | 自建或 IdP；不走公开 CDN URL | **API 有关系校验，无会话，且 `Cache-Control: public`** |
| 后台业务 | 询盘、订单、ERP 库存价 | 独立服务或 ERP API，不塞进 CMS 运行时 | **未做，也不该塞进 Directus 扩展当运行时** |

Directus 官方文档覆盖 Next.js 多语言内容（主表 + `*_translations`）。[Directus + Next 多语言](https://directus.com/docs/frameworks/nextjs/multilingual-content) Directus Labs 提供 Meilisearch Flow 操作，说明官方也把搜索当外挂索引，而不是 Directus 内置检索。[Meilisearch operation](https://github.com/directus-labs/extensions/tree/main/packages/meilisearch-operation)

## 可对照的公开案例

规模和行业越接近，越有参考价值。

| 案例 | 规模/业态 | 组合 | 对高松的含义 |
|------|-----------|------|----------------|
| [Kinesiis 工业零件站](https://kinesiis.com/case-studies/manufacturing-product-website) | 约 2,000+ 产品，制造商官网 | Next.js + Sanity + Algolia，产品页 ISR，库存走 ERP | **单站、目录不大时，CMS 结构化产品 + 独立搜索是成熟捷径** |
| [Climate Shop](https://kreatifklub.com/work/climate-shop-commerce/) | B2B/B2C 目录 + 交易 | Directus 同时做 CMS 和 PIM，Meilisearch，R2 | **Directus 管产品不是野路子，但他们把交易和搜索拆出去了** |
| [KROHNE](https://rheinschafe.com/case-studies/krohne-messtechnik/) | 工业仪表，多国站 | Akeneo PIM + Statamic CMS + Next.js + 中央 API + Cloudinary | **复杂产品 + 多国：PIM 管产品，CMS 管栏目树** |
| [Schlüter Systems](https://www.intentive.de/cases/relaunch-for-schlueter-systems) | 1 万+ 产品，20+ 国 | Pimcore PIM + DAM + 无头内容库 + 联合搜索 | **SKU 量级接近高松；他们为多国和资料治理上了 PIM，不是因为 1 万这个数字本身** |
| [ROTHENBERGER](https://www.storyblok.com/cs/rothenberger) | 多品牌、30+ 国站 | Storyblok CMS + 中央 PIM + React | **多品牌多市场才把 PIM 当骨干** |
| [HBM Machines](https://www.labdigital.nl/work/hbm-machines) | 七国市场 | Next.js + Storyblok + Akeneo + Algolia | **前台/内容/产品/搜索四件套，和上面分层同一张图** |
| [CMSNL 配件](https://www.youweagency.com/case/commercetools-cmsnl) | 欧洲配件目录 | Pimcore + Meilisearch + Next.js（另有商城） | **Meilisearch + Next 做零件检索是现成组合** |
| [BYK 产品门户](https://www.dotsource.com/references/success-stories/byk-product-portal/) | 化工产品门户 | Storyblok + 独立搜索索引 + 云存储文档 | **搜索不打 PIM；文档独立存** |
| [菲尼克斯电气](https://eclass.eu/en/application/best-practice/detail/using-eclass-at-phoenix-contact) | 集团工业连接器 | PIM 为单一来源，输出官网/印刷/电商店/数据表；ECLASS、ETIM、BMEcat | **这是数据枢纽，不是建站选型。高松若将来要给经销商标准目录，PIM 才变成刚需** |

Atlas Copco、Fersa 等案例会再加 commercetools/Adobe Commerce。高松当前没有全站交易，不必为了对齐「大厂」先买商城引擎。

## 产品主数据：CMS 表够不够，何时上 PIM

公开讨论里的分界大致是：

- **一个前台、一个运营团队、属性相对稳定、主要目标是官网：** 结构化 CMS（Directus/Sanity/Strapi）或轻量 PIM 都能做。Kinesiis、Climate Shop 走这条。
- **多站点/多品牌、完整性校验、多团队翻译、经销商/CAE/印刷要同一份资料：** 专用 PIM（Akeneo、Pimcore）价值高。KROHNE、Schlüter、ROTHENBERGER、菲尼克斯走这条。

1.3 万订货号本身不是分界线。Schlüter 1 万+ 上 Pimcore，是因为 20 国和资料理解成本；菲尼克斯上 PIM，是因为要同步分类标准和多种输出格式。

当前 `product` / `series` / `category` + 翻译表符合「产品不是一篇文章」。缺口是 `product_spec` 仍接近「每行一条已翻译参数」，缺少属性定义、类型、单位、可选值、适用产品族。这是目录做大之后筛选和导入会痛的地方，也是以后接 PIM 时要对齐的边界——不是换 Next 的理由。

## 对当前方案是否可行

可行，条件是承认 Directus 的职责边界。

| 能力 | 判断 |
|------|------|
| 营销页、新闻、方案、多语言栏目 | Directus 适合，已在做 |
| 1.3 万 SKU 详情页 | Next ISR + 关系库可行；页数不是问题 |
| 分类/系列导航 | 现模型可行；试点 SKU 未挂系列是数据问题 |
| 参数展示 | 试点够用 |
| 按极数/间距等筛选全库 | 需要属性字典 + 搜索索引，不能靠抽 `product_spec` 临时拼 |
| 多语言检索 | Meilisearch/Algolia 一类；Directus 过滤不是生产搜索 |
| 会员下载 | 必须独立鉴权 + 私有存储 + 短时链接；现接口不能上线当正式入口 |
| 询盘/订单/选型运行时 | 可把数据表放 MySQL/Directus，运行时不要做成「全靠 Directus 扩展扛交易」 |
| 以后加 PIM | 只要 ID、属性、翻译状态、文件权限先定住，PIM 可当上游，前台不用推倒 |

和 Codex 那篇复评的差异：本文更强调「流行方案是分层而不是某个品牌组合」；结论同向——继续现基座，补搜索、属性治理、受控下载和生产存储，而不是改用大型 PIM 或重写前台。

## 建议怎么用这份调研

1. 对内对外都按四层说话：内容后台、产品库、搜索、前台。会员下载是第五层，不要画进 Directus。
2. 全量迁移前仍用四个样本卡自己：复杂族导入编辑、全目录筛选、登录/未登录下载、发布后缓存与压测。
3. 只有出现这些信号再立项 PIM：要输出 ECLASS/BMEcat、多品牌多站共用一份产品、运营编不过属性一致性、或 Directus 批量改规格明显慢于专用 PIM。

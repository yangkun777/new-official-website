# 旧后台能力与当前 Demo 基座差距审计

日期：2026-10-08  
范围：旧后台源码快照 `E:\degsonen\degsonEn`、当前 Directus schema、当前官网 Demo 代码  
结论性质：只读审计，不包含本次开发改动

## 一、核心结论

旧后台值得保留的是“内容运营能力”，不是“每个语言站点复制一套 PHP 项目”。

旧系统虽然通过中文站、英文站、德文站等独立配置和站点代码实现多语言，导致维护、发布、模板和数据容易重复，但它在编辑表单层面已经具备一些当前 Demo 尚未补齐的能力：

- 图片本地上传、图片库选择、预览、清除；
- 产品多图和附件字段；
- 产品技术参数、认证图片、证书、下载、商业数据等运营入口；
- 产品批量导入；
- 栏目/分类、系列、内容、推荐位、标签、碎片、模板等内容运营能力；
- 管理员、角色、操作日志、附件管理等后台治理能力。

当前 Demo 的方向是正确的：用一套模型承载多语言，通过 `*_translations` 管理语言内容，避免复制多个 PHP 站点。但现在更像“数据骨架 + 基础展示 Demo”，还没有达到旧后台的完整运营闭环。

## 二、旧后台已确认的媒体能力

旧后台的通用表单组件在 `runtime/content_form.class.php` 中为图片字段生成：

- 本地上传；
- 从图片库选择；
- 图片预览；
- 清除图片；
- 图片地址回填。

旧内容模型 `runtime/Data/Model_field_16.php` 中至少存在：

- `thumb`：图片；
- `thumb1`：图片；
- `thumb2`：图片；
- `file`：附件。

这说明旧系统的图片能力不是前台写死，也不是单纯手填 URL，而是后台内容模型的一等字段。

旧系统对应证据：

- `E:\degsonen\degsonEn\runtime\content_form.class.php:556`
- `E:\degsonen\degsonEn\runtime\Data\Model_field_16.php:1`
- `E:\degsonen\degsonEn\xhr20210826\Tpl\Admin\Category\edit.html:196`

线上后台地址也做了只读访问：未登录访问会返回“请登录后进行操作”，并跳转到管理员登录页；本次由用户在验证码环节手动完成登录，之后仅查看页面和表单，没有保存、删除、导入、导出或发布操作。

截图展示的是“产品分类”编辑表单，但它能代表旧后台通用图片字段的交互方式；不能直接据此断定截图中的字段就是 SKU 主图。

## 三、线上后台只读核验结果（2026-10-08）

本次登录后的实际菜单和表单进一步确认了旧系统的产品运营拆分：

- “产品管理”下至少有产品总览、产品认证图片、产品技术参数、产品认证、产品附件、产品商业数据、产品下载、配套产品、关联产品、近似规格产品等独立入口；产品侧还有产品分类、系列管理、产品认证库、技术参数库、产品选型配置、栏目 Banner、颜色管理。
- 产品总览的新增表单主要是语言、订货号、产品优势、发布时间；它本身没有看到主图上传字段。因此，不能把旧系统的“产品总览”直接等同于“SKU 主图管理”。
- 产品认证图片的新增表单是语言、订货号和“认证图片（认证库 ID，多个值用 `|` 分隔）”，说明产品与认证图片库是间接关联关系。
- 产品认证库的新增表单包含标题、外部链接、图片，并提供“本地上传”“从图片库选择”“预览图片”“清除图片”，这是实际的图片资源管理入口。
- 产品技术参数、产品认证图片、产品附件、产品下载均按语言和订货号查询，并支持添加、导入、导出、审核、取消审核、批量删除、移动、复制等运营动作。
- 产品认证图片列表实测显示约 137,514 条记录，产品技术参数约 153,844 条，产品附件约 218,427 条，产品下载约 419,705 条；这说明这些不是少量补充字段，而是需要独立建模和分页运营的大型业务数据集。
- 产品附件列表除了订货号、语言外，还有标题、关联栏目等字段；产品下载列表中能看到 3D、CAD Data 等下载类型，说明下载内容需要标题/类型/文件或链接/关联 SKU 的结构，而不是一个简单 URL。

这次在线核验修正了一个重要判断：当前 Demo 缺的不是“在 product 表上补一个 image 字段”这么简单，而是缺少以 SKU/订货号为中心的产品内容聚合层，以及媒体、参数、认证、附件、下载、关联关系的运营模型。

## 四、当前 Demo 已有能力

当前 Directus 业务集合主要是：

- `category` / `category_translations`；
- `series` / `series_translations`；
- `product` / `product_translations`；
- `news` / `news_translations`；
- `languages`；
- `site_settings`。

当前已具备：

- 分类、系列、SKU 基础关系；
- 中文/英文翻译行；
- 发布状态；
- 分类和系列图片 URL 字段；
- 新闻封面 URL 字段；
- Directus 文件库基础设施；
- 前台分类、系列、新闻页面；
- hreflang、语言 slug、SEO 基础元数据和分页读取。

## 五、已确认的差距

### P0：必须补齐，否则运营无法正常维护

| 能力 | 旧后台 | 当前 Demo | 结论 |
|---|---|---|---|
| SKU 主图 | 有图片字段和上传/图库/预览/清除 | `product` 没有图片字段 | 必须补 |
| 分类图片 | 有图片上传控件 | 当前是字符串字段，未接媒体控件 | 必须补 |
| 系列图片 | 有图片上传控件 | 当前是字符串字段，未接媒体控件 | 必须补 |
| 新闻封面 | 有图片/内容媒体能力 | 当前是字符串字段，未接媒体控件 | 必须补 |
| 附件/下载 | 有附件字段和文件库选择 | 当前没有 `download` / `media` 业务模型 | 必须补基础模型 |
| 产品详情 | 有内容、图片、参数等编辑入口 | 当前只有产品变体主表和翻译行，前台暂无 SKU 详情页 | 必须补 |

### P1：产品内容管理闭环

旧后台菜单和 PRD 都指向以下能力，当前 Demo 尚未形成对应集合或界面：

- 技术参数定义、参数值、单位、筛选；
- 产品认证、认证图片、证书文件；
- 产品附件、产品下载；
- 产品商业数据；
- 配套产品、关联产品、相似规格产品；
- 产品选型配置；
- FAQ；
- 产品图片/媒体的 alt、caption、来源/版权和引用关系；
- 产品批量导入和导入结果校验。

旧快照中的动态栏目名称还明确包括：产品附件、产品技术参数、产品认证、产品认证图片、产品下载、产品商业数据、产品选型配置、配套产品、关联产品、近似规格产品、产品照片检索、系列管理、下载中心、新产品通讯、我的下载和产品对比等。

### P1：后台治理和发布能力

旧后台已经有管理员、角色、日志、附件管理、缓存/静态页生成等能力。Directus 原生已有一部分基础设施，但当前基座还没有针对官网运营流程配置：

- 编辑/审核/发布角色边界；
- 草稿、审核、发布状态的明确规则；
- 发布前必填和媒体可用性校验；
- 导入预览、错误明细、可重试；
- 资源替换影响范围提示；
- 操作审计和回滚策略。

### P2：不建议照搬

- 每个语言站点一套独立 PHP 项目；
- 每种语言复制一套内容表和模板；
- 通过生成静态 HTML 代替统一内容 API；
- 把图片、参数、证书、下载全部塞进富文本；
- 依赖文件名作为图片 alt；
- 只保存图片 URL、不记录媒体引用关系和版权信息。

这些做法是旧后台的历史实现方式，不是应该继承的产品能力。

## 六、当前基座的设计判断

### 应该保留

- 单一 Directus 实例；
- `product` / `series` 主表与 `*_translations` 翻译表分离；
- SKU、系列码、订货号等语言无关数据放主表；
- URL、hreflang、页面内容从统一语言模型生成；
- 业务数据与后台界面配置分离；
- 先做只读迁移审计，不直接猜旧分类映射。

### 需要调整

- 图片字段从普通字符串 URL 升级为可运营的媒体字段；
- 产品主图、系列图、分类图、新闻封面明确归属和回退关系；
- SKU 不能只作为系列下的一行参数，还要有可访问的产品详情内容承载；
- 增加下载、附件、参数、认证、关联产品等可扩展模型；
- 后台字段配置不能只解决中文名称，还要解决编辑器、上传器、选择器、预览和校验。

## 七、建议的后续顺序（本次不执行）

1. 先冻结媒体归属规则：SKU 独立主图、系列默认图、SKU 覆盖图的回退关系。
2. 盘点旧模型 `thumb/thumb1/thumb2/file` 到新模型的字段映射，不直接把旧字段名照搬成业务 API。
3. 设计统一媒体模型：文件、用途、语言、alt、caption、版权、引用关系、排序。
4. 先在 Directus 做一个 SKU 媒体最小闭环：上传、图库选择、预览、替换、清除、API 读取。
5. 再补分类、系列、新闻封面的同一套媒体能力，避免各做一套。
6. 再补产品详情、参数、认证、下载、关联产品和批量导入。
7. 最后配置角色、审核、发布校验、审计和回滚。

在第 1 步没有冻结之前，不建议直接给 `product` 加多个图片字段或直接迁移旧图片；否则后续很容易出现“系列图、SKU 图、认证图、正文图”混在一起，迁移和前台展示都难以追溯。
